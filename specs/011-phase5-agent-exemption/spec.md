# 011 · Phase 5 受控 Agent 自动化 — 豁免口径（按设计未实现）

对照 `docs/PLAN.md` 阶段 5 与「五、安全边界」第 5 条。**结论：按设计豁免**——当前版本刻意不做执行器，这不是缺口而是安全边界的执行。

## PLAN 验收标准 vs 当前立场

| PLAN 验收标准 | 当前状态 |
|---|---|
| 未经确认的高风险操作无法执行 | ✅ 由架构保证：**不存在执行器**。审批模块只记录批准/拒绝状态（`app/api/main.py` approvals 三路由），没有任何代码路径消费批准结果去执行文件修改/命令/消息发送（`docs/PLAN.md` 安全边界第 1 条明文约束） |
| 批准后的操作只能在已授权范围内执行 | 不适用（无执行器） |
| 工具注册、白名单、权限校验、审计日志 | 「待审批动作」以 `POST /api/approvals` 记录（action_type + payload JSON + status + reviewed_at），即审计链的录入端；执行端留待阶段 5 启动 |
| 失败恢复 | 不适用 |

## 启动条件（何时解除豁免）

1. 记忆质量与建议闭环稳定运行一个观察期（phase 2/4 的反馈数据可用）。
2. 执行器必须按 PLAN 第 5 条完整实现：工具注册 → 白名单 → 参数与权限校验 → 待审批 → 确认 → 受限执行 → 审计 → 失败恢复；一次批准不等于授权所有类似操作；执行前重新检查路径/权限/文件变化。
3. 届时在本目录补 `spec.md`（FR 化）与契约测试，禁止跳过审批直连执行器。

## 与现有代码的衔接点

- `approvals` 表已含 `action_type`/`payload`/`status`/`reviewed_at`，是未来执行器的事件源。
- 通知渠道当前为 fake channel（`notification_delivery.FakeNotificationChannel`），执行器落地的通知面同样先走 fake。
